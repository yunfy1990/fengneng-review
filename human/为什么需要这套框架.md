# 一套自己长出来的项目评审框架

> 这篇是给**人**读的。给 agent 用的那份在 `skill/`（`SKILL.md`）。
> 两份东西是同一套机制，只是消费面不同。

---

## 一、先说它解决什么问题

**先看适不适合你（三条，30 秒）**：

| | |
|---|---|
| **适合** | 你手上有一个"到底要不要做"的项目、工具或习惯，事后说不清为什么；或你已经在用 AI，但不知道它是在帮你还是在给你派活。 |
| **不适合** | 你要的是"该不该做"的**结论**——这套东西不给结论，它给的是一段能被复核的**过程**。 |
| **可跳过** | 只想用现成清单 ⇒ 直接看文末「怎么用」；只想读故事 ⇒ 从第二节开始；完全不想读 ⇒ 关掉，这东西本来就该被跳过。 |

**一个最小示例**（三十秒读完）：

> 要做一个"每天早上给我推摘要"的机器人。你觉得它省事。
> 框架会问你：**产出落到你面前是什么形态？**（一条结论 / 一份清单 / 一批待办 / 一本持续追踪的账 / 静态文档）
> 如果是"一批待办"——那它不是省事，是把活推给了你。结论：**改成触发式查询**。
>
> 就这一步，它已经替你避免了两个烂尾项目里的同一种死法。

---

"这个项目该不该做？"——这个问题几乎每个人都会问，也几乎每个人都答错。

错的答案通常长成两种：

- **凭感觉开工** → 做完发现不值，于是烂尾；
- **凭感觉砍掉** → 砍掉了本该做的那一件，而且事后没人说得清为什么。

问题不在于你没有直觉。问题在于**你的直觉拿不出证据**，于是没法说服别人，也没法说服三个月后的自己。

这套框架不给你答案。它给的是**一段能被复核的判断过程**。

它要回答的核心问题只有一个：

> **这件事带来的丰容（心理、社交、物理感官的丰富度），
> 和它消耗的精力——包括被 AI 加速之后反而变多的那部分——是不是划算。**

---

## 二、它长出来的地方：两个烂尾的项目

这套框架不是我坐在桌前想出来的，是被两个失败的项目逼出来的。

**第一个**：我往一个机制里记笔记，后台不断去挖这些笔记里可能蕴含的人物画像认知，然后推送给我、让我确认。

**第二个**：我转发一些觉得有意思的公众号文章进去，它在凌晨解析完加入队列，等我有空的时候过去判断——是不是真的有价值，跟我在做的项目相不相关。

两个都烂尾了。而且烂尾的方式一模一样：

> 我记得越多、转发越多，它产出的就越多；而我的精力有限，中途还转移去了别的项目；于是待确认的越积越长，心理压力越来越大，最后**眼不见为净**。

拆开看，是同一句话：

**AI 产出的速度 > 人消化的速度 ＝ 积压 ＝ 心理压力 ＝ 烂尾。**

这不是执行问题，是设计问题。所以判据落在三问上：

> **最终消化端点站在哪一边？**
> ① 你**愿意**消费它吗？
> ② 它能被**无成本忽略**吗？
> ③ 被迫处理的量与收益相称吗？

AI 自己消化完、只给你最终可执行的结果 → 这是节能。
AI 产出洞察、你逐条确认 → 这是负担。

还有第三种情况，不属于上面两档：**AI 产出了，但没有人消费**。这不等于浪费，是**待查风险** ——
要回答四个问题：它的用途是什么？还能等多久？保留它要花多少成本？删掉会有什么后果？

**不为证明"有人消费"而制造阅读任务。**

更麻烦的是，第二件事我一开始完全没看出来。当时仓里所有关于"它们为什么烂尾"的描述，其实都是 AI 转述出来的，转述互相引用，搭成一个看起来很完整、实则没有人核对过的自证链。

**直到我自己把当时的原话重新录了一遍。** 源破了，结论才立得住。

这件事后来成了框架里的一条硬纪律：**证据链要能追到一手来源**。

## 三、框架本体：四个维度

评审时按顺序过四道。

### 维度一 · 丰容价值

- 这个项目带来什么类型的丰容？认知的、社交的、还是物理感官的？
- 它的**边际效用曲线**如何？一开始兴奋，多久开始递减？有没有"做着做着变成负担"的风险？
- 它是**基本盘**还是**可调节增量**？基本盘不能砍，增量可以动态调。

> 这里有个反直觉的区分：**基础设施类的项目容易被系统性低估**。它不直接给你快乐，但它是别的快乐的地基。所以维度一里专门有"间接丰容"这一问。

### 维度二 · 节能价值

- 它是真的省精力，还是只是把精力换了个地方花？
- **长期净节能还是净耗能？** 有些事短期耗能、长期节能（运动、学习、写作）。有些反过来。
- 有没有"越用越沉没成本"的东西？

### 维度三 · 平衡与风险

- 遇到问题时能不能停下来？出事的话损失什么？
- **运维成本谁来做？** 口径是：**时间 + 费用 + 故障善后 + 权限风险**。agent 执行不耗人时间，但后面三项不会因为 agent 执行就归零。
- **读操作 vs 写操作的权限分级**：写账本、写外部系统、云端上传、归档落盘——读写风险**不对称**，四铁律看不见这个区分。
- **产出物的形态**：落到你面前的是一条结论、一份清单、一批待办、一本持续追踪的账，还是一份静态文档？**形态决定它是不是负担。**

### 维度四 · 铁律兼容

- 触碰了哪些既有的硬约束与禁忌？
- 你是 agent 提炼的风险提示，还是作者本人明确规定的禁忌？**这两者的否决效力完全不同。**

## 四、评审闭环：结论之后才是重点

一份评审报告本身没有价值，有价值的是它后面发生的事。

1. **结论必须落在六态之一**：继续 / 限额试验 / 缩减 / 暂停 / 停止 / 接受残余风险。
   不接受"再看看"这种结论。
2. **只被采纳的承诺才写成硬谓词**。硬谓词 = 截止日期 + 可检查的完成标准 + 验证方式 + **「证明什么」标注**。
   "证明什么"这一栏最容易被忽略，但它决定这条待办会不会变成一句空话：

   | 标注 | 含义 |
   |---|---|
   | 证明**实现存在 / 运行事实** | 能用 grep / ls / exit code 判定 |
   | 证明**结果 / 价值** | 需要有人判断，且**不许伪装成机器谓词** |

   存在性证明不能充当价值结论。这条我吃过亏。

3. **每次评审记录"框架体感"**——这次评审让我觉得哪里别扭。累计到阈值就触发**框架复盘**，复盘只改问法，不改结论。
4. **机械闸只验证格式与事实，不替代语义判断**。自动脚本能确认字段齐不齐、数值对不对，判断不了"这个项目到底值不值"。

## 五、证据纪律：这部分可能比四维度更值钱

四条，都来自真实教训（不是从原理推出来的）。

**① 文档 ↔ 实现必须对读。**
文档写着"一律推送"，实现里却有个前提条件——这是纸面规则，不是行为。**规则文本和执行现实不一致时，这段规则不能证明被执行。**

**② 问一句：触发条件当前是否可能成立？**
永不成立 ＝ 纸面条款候选（该删或该修）。长期成立却没有对应动作 ＝ 噪声或失效候选。
只标记，不自动删——删规则是人的决定。

**③ 单次成功只证明"发生过"。**
要下"稳定""可靠"这类结论，必须**重复运行，并报出次数 n 与失败数**。样本不足就标"待验证"。
"首跑成功 → 长期有效"是最常见的一次推断跳跃。

**④ 独立验证有层级。**
"不同源"只是起点。合格的独立层必须能接触**原始凭证**、**自由选择检查方法**、**报告不同结论**。
只能对着你的摘要背书的，叫第二意见，不叫独立验证。

## 六、边界声明（请认真读这一段）

**这套框架解决不了系统级问题。**

它处理的对象是**单个项目 / 产品 / 重大功能**。当问题的对象是"若干局部机制之间的相互关系"时——比如"每一个局部的产出，都可能变成另一个局部的投入"——本框架**不提供判据**，需要升到系统视角单独处理。

这不是谦虚，是设计边界。很多看起来是"这个项目该不该做"的问题，到最后发现是系统问题——那种时候硬套四维度，只会给出一个看起来很完整的错误答案。

还有两条：

- 框架**只产出判断与风险提示，不产出授权**。否决权仅属作者明确规定的禁忌范围。
- 四条铁律是从真实烂尾案例里提炼的**场景化风险提示**，**未经普遍化为所有机制的禁忌**。它提醒你，不替你决定。

## 七、怎么用

### 给 agent 用

把 `skill/` 放进你的 skill 目录（兼容 `SKILL.md` frontmatter 的客户端都可以），然后按 `skill/SKILL.md` 的「什么时候用」触发：

> 新开一个个人项目或事务目录前 / 给已有项目加重大功能或新方向前 / 犹豫"这个东西要不要做"的时候

配套的格式校验脚本可以单独跑：

```bash
python -X utf8 scripts/fengneng_review_lint.py --selftest
```

### 给人用

四道维度照着问一遍，结论落六态之一，被采纳的承诺写成硬谓词并挂账，然后——**别忘记录这次的"别扭感"**。那才是下一版框架的输入。

## 八、致谢与来源

这套框架是在既有材料之上做的组合与改造——相关领域已有先例（人-AI 协作指南、项目阶段门治理、
AI 风险管理框架里的非金钱成本与残余风险接受等）。设计之初专门查过，**未找到同一完整组合，
