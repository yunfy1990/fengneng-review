# 丰容/节能项目评审框架

> v1.13（2026-10-30 第五轮复盘，作者拍板「同意你的倾向」）：补强机制证据链与独立性、分开重评与记账、区分单次成功与可靠性、净节能对照既有做法。逐条处置见评审记录台账第五轮；上一版 = v1.12，溯源见 `references/HISTORY.md`。本框架是在既有材料之上做的组合与改造（相关领域已有先例，未找到同一完整组合但不等于首创），需在使用中迭代。
> 修订历史已外置（2026-10-20 分层；本文件只留操作核心）——什么时候读 → 见文末「references 索引表」。归位判据见「分层与归位规则」。
> 框架内容单一事实源 = 本文件；评审日志 = `REVIEW_LOG.md`（skill 目录只放定义，运行数据放项目归属地）。
> 记账位：每次评审写入上述 评审记录台账（项目名/日期/四维度结论/框架体感反馈）；有条件过的条件挂 `TRACKING.md（待办追踪）` 追踪；框架复盘触发由机械闸扫描（口径见第 9 步）；偏差来源=作者评审后的体感反馈；回流到=本文件的框架维度与问法。

## 什么时候用

- 新开一个个人项目/事务目录前
- 给已有项目加重大功能/新方向前
- 犹豫"这个东西要不要做"的时候
- 作者说出触发词：丰容评审 / 新项目过一下 / 这个项目要不要做 / 项目评审

## 四维度检查清单（v1）

### 维度一：丰容价值

- 这个项目带来什么类型的丰容？（认知 / 社交 / 物理感官）
- 丰容的边际效用曲线如何？（一开始兴奋，多久会递减？有没有"做着做着变负担"的风险——参考「产出找人确认」型机制/「资料转队列」型机制烂尾模式）
- 它是"基本盘"还是"可调节增量"？（基本盘不能砍，增量可以动态调）
- **间接丰容（v1.3 新增）**：这个项目是否通过赋能其他项目产生丰容？（工具类/基础设施类必须问——本身不直接丰容，但下游项目的丰容有一部分归功于它）

### 维度二：节能价值

- 替我省了什么？（认知 / 体力 / 时间 / 决策）
- **消化端点在哪一侧？**（v1.7 由等式改三问——"AI 替人消化 = 节能 ✅ / AI 产出给人消化 = 负担 ❌"只是启发式，不是等式；自愿选择的高认知投入（学习/审美/对话）可能本身就是价值）：
  1. 人是否**愿意**消费这个产出？
  2. 这个产出可否**无成本忽略**（不看也不欠账）？
  3. **被迫处理量**与收益是否相称？
- **第三态（v1.7 新增，来自另一协作方 B 评审体感）**：「AI 产出但无人消费」不直接等于浪费，是**待查风险**——结合四问判断：用途是什么 / 等待期限多久 / 保留成本多少 / 删除后果如何。低成本留存的备用资料可能只是还没到使用时机；**不为证明消费而制造阅读任务**。
- 运维成本多少？（上线后需要多少持续维护精力？有没有创造新的"必须做"的事情？）
- **长期净节能（v1.3 新增，v1.13 补对照）**：短期耗能但长期节能的项目（运动/学习/健康），净效应怎么算？**与没有本项目时的既有做法相比，人 + AI 是否整体更好？** 纠错、监督、学习成本也计入；简单前后或流程对照即可，不强制量化或随机试验；无法对照标「待验证」，不宣称净节能。

### 维度三：平衡与风险

- **问题有效性（v1.4 新增）**：这个项目/实验要回答的问题本身存在吗？无论结论正反，会不会改变你的行为或决策？结论注定是废话直接判"不过"。**更深一层：框定问题的概念是从前提推导的，还是自己引入的？** 警惕概念偷换（如从"消化负担"滑到"沉迷"，滑过去整个方向就偏了）
- 丰容/节能比如何？（v1.7：只作参考信号，不作负面默认——休闲无需证明生产收益，基础工具无需有趣；判结论按实际目的/负担/机会成本）
- 跟现有项目的关系？（互补 / 竞争注意力 / 重复造轮子）
- **运维成本谁来做（v1.3 新增，v1.7 扩项）**：agent 做还是人做？比例多少？成本口径 = **时间 + 费用（LLM/服务账单）+ 故障善后 + 权限风险**——agent 执行不耗人时间，但其余三类不因 agent 执行而归零（实证 = 某交易域 SOP L1 评审，溯源见 HISTORY v1.7）
- **读操作 vs 写操作的权限分级（v1.9 新增）**：**本项目会不会写？**（写账本 / 写外部系统 / 云端上传 / 归档落盘）——读写风险**不对称**，四铁律看不见这个区分；实证 = 某记账类助理 MVP 同一项目输出侧无条件过、输入侧有条件过（溯源见 HISTORY v1.9）。**条件式问法：只在涉及写入时必答**。
- **读侧内容敏感度（v1.12 新增）**：**本项目读什么数据？里面有什么（含多少个人信息）？**——纯只读**不豁免**：只读管道照样能把隐私内容搬进报告/推送/资料柜；**条件式：读取面涉个人信息/凭证/他人内容时必答**（读写分级管权限不对称，本条管内容敏感度）。实证 = 某技能审计任务的隐私边界靠硬谓词钉住（溯源见 HISTORY v1.12）
- **自建闸自证与独立验证（v1.12 新增，v1.13 补强）**：**闸/口径谁定义、自检谁跑？**——**条件式必答：机制类、涉写权限、涉历史口径改写三者居其一**。**机制类还须做文档↔实现对读；有既有日志时抽一条真实轨迹核对最终结果，不要求新建全量追踪。规则触发条件当前是否可能成立？** 永不成立 = 纸面条款候选；长期成立却无动作 = 噪声/失效候选，只标记不自动删。**不同源只是独立性起点**：独立层须能接触原始凭证、自由选择检查方法并报告不同结论；只能对摘要背书 = 第二意见。（本条针对**高风险 / 涉写 / 涉历史口径**；低风险纯只读自检由作者自己核即可，不强制独立层。）手段分层：常态 = 外部哨兵 + 作者抽检；择机 = 外部盲评（能算出不同数字或给出穿闸错误类别，不接受背书式回信）；对拍 = 关键数字管线逐步引入第二实现。实证见 HISTORY v1.12/v1.13
- **监督形态（v1.8 新增）**：自动化/无人值守类项目必问——监督形态变了吗？人是否失去当场打断能力、唯一监督只剩告警？（依据 = OWASP "human approval for high-risk actions"；**人失去打断能力本身是风险**——最大风险不是"运维多不多"，而是"人还在不在回路里"）
- **输入端喂养队列（v1.8 新增）**：输入端动作本身会不会喂养队列？记笔记/转发/收藏等低摩擦输入是否被机制转化为需要人消化的输出？——消化端点在 AI 侧只是必要条件之一，还要查输入端（控燃料比控人侧意志力可靠）
- **历史口径与历史数字的改写（v1.10 新增）**：**本次改动会不会让已发布/已归档的历史数字变？** 若会，正本须同时给出①新旧数字对照 ②哪条旧结论**失效** ③是否需重算年度/期间报表。判"不适用"的标准 = 不触碰任何已发布数字（纯新增功能/纯 UI/纯文档）。实证 = 某记账类项目调整一类历史记录的归属口径，使多个历史年度的支出统计随之变化（溯源见 HISTORY v1.10）
- 退出策略？（什么条件下可以放弃/暂停？烂尾了怎么收尾不留下心理债务？自然结束类项目标注"不适用"）
- 时间预算有没有上限？（内容类问"规划截止日"，机制类问"每日/每周触发频率上限"）

### 维度四：铁律兼容

> **v1.7 定性（重要）**：四条铁律是 agent 从两个烂尾先例与 ChatGPT Pulse 提炼的护栏，**未经作者普遍化为所有机制禁忌**。因此：
> - 本维度只产出**场景化风险提示与取舍**；**只有作者明确规定的禁忌才有否决效力，且仅在其授权范围内**。
> - TTL / 健康锚 / 静默归档等是候选缓解，不是自动豁免；判据 = **是否制造非自愿义务与打扰**，不是形式上有无队列/定时任务。后台主动运行 ≠ 打扰；**禁止"这是'该做的事'队列所以豁免"的循环论证**。
> - 机制类审查强度升高，工具类/事务类标注"不适用"；溯源见 HISTORY v1.7。

- **产出物的形态（v1.9 新增）**：**本项目的产出物落到作者面前是什么形态？**（单条可执行结论 / 清单 / 一批待办 / 持续追踪的账 / 静态规则文档）——**形态决定它是不是负担**。**四问之外先问形态，再问铁律**；实证见 HISTORY v1.9。

- 零队列？（会不会产生需要人**非自愿**逐条确认/处理的积压？**区分队列性质（v1.8 明确，源自 待办追踪机制评审体感）**：待办队列 = 该做的事、有截止、做完翻篇（如 待办追踪（挂账））；**它不因为"这是该做的事"而豁免**（那是循环论证）——豁免依据是效果：每条都有截止、做完即翻篇、未到期静默不打扰；消化队列 = AI 产出给人逐条消化，才是铁律防的对象——别看有没有队列，看队列里装的是什么）
- 纯触发？（主动推送/定时调度是否构成**打扰**？还是安静后台运行？）
- 干预完即翻篇？（会不会需要持续追踪/跟进？）
- 单条输出？（是一条可执行建议还是一堆选项矩阵？）

## 参数基准表（v1.1 新增）

评审中涉及量化阈值时，优先查表，不现场拍脑袋。表中数据从仓内历史提炼，持续校准。

| 参数 | 基准值 | 来源/依据 | 备注 |
|---|---|---|---|
| 两个烂尾先例的存活时长 | **时长未核；不提供通用平均寿命阈值** | 作者原始口述（原始口述档（未随包发布））只含两例「积压→心理压力→眼不见为净→烂尾」的过程描述，**无任何时长数字**；v1.6 前标注的"2–3 个月有效产出期"系 agent 估算、"2026.02–09 约 7 个月全周期"系仓内既有记载（起止以作者记忆为准），二者均**不得标注为作者原话支持** | 无通用预警阈值；存活/预警一律个案判断 |
| 新项目观察期 | 2 周 | 低风险实验惯例（实验登记表.md） | 2 周内无正反馈可考虑收回 |
| 项目退出阈值 | 连续 2 周零投入且无计划 | 仓内项目活跃模式 | 不等于失败，是正常归档 |
| 单项目周运维上限 | ≤ 2 小时/周（建设期满后） | 待校准——基于作者可支配时间估算 | 建设期（前2周）不受此限 |
| AI 项目总时间预算 | 待作者确认 | 目前无明确数字 | 建议作者给一个"每周愿意花在AI项目维护上的总时间" |
| 旅行项目规划周期 | 1–2 个月 | 作者历史项目均为此模式 | 超过2个月仍未出行需检查是否卡在决策上 |
| 干预响应延迟 | 触发后 ≤ 1 轮对话内给出单条建议 | 铁律"纯触发+单条输出"的自然推论 | 超过1轮=变成了讨论，不是干预 |

**使用方式**：评审时引用表中值作为默认参数，如项目有特殊情况可偏离，但需在建议中说明理由。表中"待校准/待确认"项在后续评审中逐步填充。引用表中任何数值必须同时给出来源与适用范围；n<3 的个案提炼一律标"暂定"。矩阵定位（甜品/沉迷/苦修/烂尾/中间）仅是导航索引，不作结论依据；象限名对活动/内容类不含褒贬——「沉迷区」对高丰容低节能的活动类项目（如周末出行）是合理落点，不是负面标签（v1.8 注释）。

## 输出格式

每次评审输出固定结构，方便跨项目对比和后续框架迭代：

```
## 评审：<项目名>（YYYY-MM-DD）

**结论**：✅ 过 / ⚠️ 有条件过 / ❌ 不过
**终态**：<v1.9 新增 · 六态决策：继续 / 限额试验 / 缩减 / 暂停 / 停止 / 接受残余风险。**与「闭环状态」不是一回事**——闭环状态 = 跟踪进度，终态 = 决策结论。多数条目 = 继续>
**矩阵定位**：<甜品区 / 沉迷区 / 苦修区 / 烂尾区 / 中间区>——基于丰容价值×节能价值的高/低二分，中丰容+中节能放中间区
**闭环状态**：<open（承诺跟踪中）/ conditions-met（条件已满足待确认）/ pending-rereview（已触发重新评审）/ closed（已归档——六态任一均可归档，不一律要求重评）/ stopped（显式停止追踪，合法终态）/ not-applicable（✅过无条件）>

**本次增量**：<v1.9 新增 · **增量评审必填**：这次评的是哪一部分（相对上一版的增量）；全量评审写"首次评审"。不写 = 读者分不清这次评的是什么——「现有产物」会把历代家当平铺>
**现有产物**：<已存在的相关脚本/文档/机制/待办追踪（挂账），列出来；没有就写"无新增，本项目为全新"。**已实现与仅设计分开列**（v1.12 新增，源自某周期复盘机制 v2 的体感——实测发现文档已声明任务、OS 任务却不存在）：调度/接线类声明以实物为准（任务记录/心跳/真实报告），不以设计稿冒充运行证据>
**业界参考**：<业界benchmark/行业标准/学术研究的来源+关键数值+是否适用+属于人-系统还是人-AI协作模式；没有就写"无成熟业界参考，阈值从仓内数据提炼">
**丰容价值**：<一句话评分 + 关键风险>
**节能价值**：<一句话评分 + 关键风险>
**平衡与风险**：<一句话评分 + 关键风险>
**铁律兼容**：<一句话评分 + 关键风险>

**条件（如有条件过）**：<仅"被采纳的承诺"才写成条件。每个条件必须是硬谓词——含截止日期+可检查的完成标准+验证方式Type A/B+「证明什么」标注（实现存在/运行事实 vs 结果/价值）；完成标准写"语义+具体定位器"，禁裸字符串 grep；同一真实决策的条件按风险合并在同一 待办追踪记录。例："<截止日>前在README写下3个具体用途（Type A：grep README 可查；证明：定位器存在，不证明：用途真被使用）">
**建议**：<如果有条件过，条件是什么；如果不过，替代方案是什么>

**框架体感**：<这次评审有没有觉得哪个维度多余/缺失/问法不好？没有就写"无">
```

> 字段标签后允许带一层括号注记再冒号（如 `**铁律兼容**（机制类，审查强度升高）：`），机械闸自 2026-10-18 起放行此变体；但冒号不可省（无冒号 = 缺字段）。

> **「结论」三分 ↔「终态」六态的对应（v1.9 新增）**——防"三分法逼出假债"：
> - ✅ 过 + **继续** = 常态（多数条目）
> - ✅ 过 + **接受残余风险** = "够用且成本可接受"的正式终态（工具类常用）——**不是**"有条件过 + 造一条待办"
> - ⚠️ 有条件过 + **限额试验 / 缩减 / 暂停** = 附条件推进
> - ⚠️ 有条件过 + **停止** = 条件不再追踪，历史存档
> - ❌ 不过 + **停止 / 暂停** = 正式结束，不留心理债务
>
> 依据：某字幕生产场景的评审体感——"不做真分词"不是"没做完"，而是"够用"的正式终态；若只有"过/不过"两分法，这种状态会被迫写成"有条件过 + 造一条待办"，反而制造假债。

> 矩阵定位是四维度评分的快速索引——用户一眼看到项目落哪个象限，比读四行维度评分效率高。完整矩阵可视化 = `docs/丰容节能矩阵.html`（2×2+1结构，中间区超3个项目时考虑升级3×3）。

### 建议的三档强度（v1.1 明确）

| 档位 | 适用场景 | 输出要求 |
|---|---|---|
| 弱建议 | 项目方向清晰、作者只需要确认 | "过，无附加条件"即可 |
| 中建议 | 有条件过/需要调整 | 给出具体条件，参数引用「参数基准表」，不现场编 |
| 强建议 | 不过/需要重大转向/agent 有明确主张 | **必须带一句因果链**："我建议 X——因为 Y（指向哪个维度的判断）"。结论+理由一体，不允许只有结论没有推理 |

强建议示例：
> ❌ 不过。我建议砍掉这个项目的"每日摘要推送"功能，只保留触发式查询——因为按作者既往体验（两个烂尾先例原始口述），"每日推送 + 逐条确认"曾两次制造非自愿义务、最终眼不见为净（维度四效果判据：制造非自愿打扰，而非形式上"有队列即违规"），且摘要需要人逐条消化（维度二：被迫处理量与收益不相称）。

## 使用流程

0. **项目类型前置判断**：先判断对象属于哪种类型，不同类型维度权重不同——
   - **机制类**（干预/提醒/自动化）：维度四（铁律兼容）**审查强度升高**（v1.7：不再是形式一票否决——输出场景化风险提示与取舍问题，否决权仅属作者明确禁忌的授权范围）
   - **工具类/基础设施**：维度一加「间接丰容」问法，维度四标注"不适用"
   - **内容类**（旅行/学习/创作）：维度三时间预算问"规划截止日"，退出策略标注"不适用（自然结束）"
   - **事务类**（一次性/明确完成标准）：直接标注"框架不适用"，不过四维度
   - **元项目**（框架/方法论自身）：维度一用"间接丰容"问法，维度四权重升高
   - **已完成项目**：只做"模式提取"，不做完整四维度评审
   - **混合体（v1.9 新增）**：现实中"工具类 × 机制类"是常态（数据基础设施 + 写入纪律 / 点单式工具 + 轻量分流），**不必新增第六类**——标「**主类 + 副类**」即可：主类按"是否产生持续执行流"判；副类**不写"不适用"**，改写"轻量检查 + 一句理由"。实证：混合体上"间接丰容"问法比直接丰容问法更能抓到价值（负面样本框架评审体感）。
1. 作者说出触发词或描述新项目
2. **现有产物核查（强制步骤，不可跳过）**：**只要 agent 说"我们来做X/新建X/设计X"，无论是否在评审流程中，都必须先查**——搜脚本（`scripts/`（本包自带））、文档（项目 README/交接文档）、待办追踪库（TRACKING.md）、calendar、CHANGELOG、实验登记表.md、`skills/`。把已存在的相关产物列出来，避免把已落地的东西当成待办。**核查结果写进输出格式的「现有产物」字段。**
3. **业界最佳实践核查（强制步骤，v1.4 新增，v1.5 扩展）**：评审中涉及**量化阈值、指标选择、方法论选型、闭环机制设计**时，先查业界有没有成熟的最佳实践——
   - **先判断场景属于哪种模式**（v1.5 新增，两种模式的最佳实践不同，不能混用）：
     - **人-系统模式**：人评审、人追踪、人验证（如安全审计POA&M、技术债务管理、项目管理）。最佳实践来源：NIST/CMS POA&M、软件工程技术债务管理、PMI项目管理。核心设计前提=防止人偷懒/忘记，所以流程重、需要named owner和固定节奏。
     - **人-AI协作模式**：AI评审、AI追踪、机械闸验证、人只做决策（如本框架的评审闭环）。最佳实践来源：agent loop 验证、Claude Code/Codex 社区实践。核心设计前提=防止AI自己骗自己（maker≠checker），所以需要独立验证者和机器可检查的成功条件。
     - ⚠️ **v1.7：该二分是检索线索，不是穷尽分类**——两类风险（人会忘/会偷懒、AI 会自证）可同时存在于同一机制；引用时按风险点分别取径，不按标签站队。v1.5 所引"Loop Engineering 共识"表述未经独立核验，已弱化，不作权威依据。
   - 有公信力 benchmark / 行业标准 / 学术研究结论 → 直接拿过来用，注明来源和适用条件
   - 没有 → 从仓内历史数据中提炼（参考「参数基准表」），或先开数据收集再定阈值，**不现场拍脑袋**
   - 核查结果写进输出格式的「业界参考」字段（来源+关键数值+是否适用+属于哪种模式）
   - 典型场景：选实验指标时查"业界用什么衡量X"、定阈值时查"行业标准是多少"、选方法论时查"有没有成熟框架"、**设计评审闭环/追踪机制时查"Loop Engineering怎么设计setpoint和verifier"**
4. Agent 按四维度逐一提问/分析（不需要作者逐条回答，Agent 可基于已有信息主动判断，存疑的才问）
5. 输出固定格式的评审结论
6. **当场追加到 `REVIEW_LOG.md`**（含框架体感）。**重评与记账分离（v1.8 合并规则，v1.13 澄清）**：step 8 管要不要重评，本步管记在哪里。同一对象同日二评/重评默认不另立完整条目，即使主版本变化须重过四维度，也在原条目追加含**结论、本次增量与四维复核**的注记；只有项目性质、权限面、用途或评审对象实质改变才另立。跨日增量可单列，条目应压缩，防评审记录台账膨胀
7. **在被评审项目的主文档加标记（v1.4 新增，强制步骤）**：
   - 待办追踪类机制 → 在frontmatter加 `version: vN` + `fengneng_review: passed|conditional|rejected|not_applicable` + `fengneng_review_date: YYYY-MM-DD` + `fengneng_review_version: vN`
   - 项目目录 → 在README.md或主文档标题下加一行 `> 版本：vN | 丰容评审：✅ 过 / ⚠️ 有条件过 / ❌ 不过（YYYY-MM-DD，vN）`
   - 目的：新开对话时读文档一眼就能看到评审状态和版本，不用去评审记录台账翻找
8. **版本号维护与重新评审触发（v1.4 新增）**：
   - 机制类/项目类文档必须有 `version` 字段（初始v1）
   - Agent修改机制文档时判断：改了核心逻辑/功能/铁律兼容性 → 升版本号（v1→v2）；改错别字/文案/参数微调 → 不升
   - 升版本号后自动检查：如果 `version ≠ fengneng_review_version` → 提醒"该机制自上次评审后有迭代，是否需要重新评审？"
   - 主版本号变化（v1→v2）→ 必须重新评审；次版本号变化 → 判断是否涉及核心维度，涉及则重新评审，不涉及则更新 `fengneng_review_version` 即可
   - **条件落地不计入版本变更（v1.8 新增，源自某交易域 SOP C4/C5 落地体感）**：落地本次评审自己开出的条件 = 按已评审结论实施，不升版；只有当落地引入了评审时未讨论过的新设计决策时才升版——否则会形成「评审开条件 → 实现条件 → 文档变了 → 必须重评 → 又开条件」的死循环
9. **复盘触发检查（v1.8 落字纪律 / v1.9 两线 / v1.11 机械判定）**：机械闸 = `python -X utf8 scripts/fengneng_review_followup.py`（宿主环境的收尾体检环节）扫评审记录台账报两线：**线① = 距上次框架复盘新增评审 ≥5 条**（**基准 = 新增数，不是评审记录台账总条数**，v1.9 修正；新增 = 当前总条数 − 最新复盘块内基线行 `<!-- fengneng:baseline reviews=N -->` 的 N）；**线② = 同一体感谱标签 `【体感谱：slug】` 出现在 ≥2 条评审里**即触发（同类事故写同一 slug，闸跨条目关联，治"同谱事件未自动关联"；不必等满 5 条——燃料是事故不是数量，理由与实证 = `references/HISTORY.md` v1.9 条目）。**人工动作不变**：触发时在当次条目「框架体感」末尾写明当前条数并提醒作者做框架复盘——**禁止只口头提醒不落字**（条目字段才是可回溯的触发留痕，此前三次自提醒因没落字而未执行）。
   - **基线行（v1.9 立，v1.11 机器化）**：每次框架复盘记录的「计数基线」行旁必须写 `<!-- fengneng:baseline reviews=复盘时评审总条数 -->`；缺它闸退化按评审日期估算并报盲区 WARN（同日晚于复盘录入的评审不可见）。

## 评审闭环机制（v1.5 新增，核心）

> **评审的终点 = 当前决策有充分证据**（v1.7 校准，废止 v1.5"最后到达完美态才真正结束"的表述——它在实操中会驱动无界复审）。合法终态六选：**继续 / 限额试验 / 缩减 / 暂停 / 停止 / 接受残余风险**。框架的角色 = "帮助作者决定什么值得继续"，不是"把项目持续改到通过"；**只有被采纳的承诺才进入跟踪**；停止/缩减/接受残余风险均为正式结束，不必回溯证明达到原通过标准。
> 本机制的闭环结构参考控制论模型（setpoint/controller/plant/sensor+comparator）。v1.5 所引"Loop Engineering 业界共识"的外部来源**未经独立核验**（2026-10-15 与另一协作方对账确认），降级为设计灵感引用，不作权威依据；Type A/B 验证分类保留。
>
> **采纳的认定路径（v1.8 明确，源自 一台备用算力机 抽样重评体感）**：①作者当轮明确拍板采纳；②作者**事先已给出明确授权**（如"按你的建议做"这类显式指令，或事前约定好的默认承接）⇒ 挂账有据；**沉默、未回复、未表态，一律不推导为采纳**；其余（含 agent 单方提出、作者未表态的条件）= 未采纳，标【未采纳·仅建议存档】——不追踪、不记完成、不因原截止制造义务。

### 控制论模型

| 控制论角色 | 映射到评审闭环 |
|---|---|
| Setpoint（目标值） | 评审结论中被采纳的承诺——写成硬谓词（Type A 机器可检查；Type B 有明确评价对象和证据形式的人类判断） |
| Controller（控制器） | AI（主笔 agent），执行后续动作 |
| Plant（被控对象） | 被评审的项目/机制 |
| Sensor+Comparator（传感器+比较器） | 机械闸（`scripts/fengneng_review_followup.py`），验证条件是否满足 |
| 收敛条件 | 六态终态决策 → 归档——继续/限额试验 = 承诺落地后归档；停止/缩减/暂停/接受残余风险可随时结束未履行承诺，无需先全部落地（不一律重评） |

### 闭环的两个必要条件（来自 Loop Engineering）

1. **可判定的成功条件**——"改善用户体验"不行，必须是硬谓词。**Type A = 机器可检查（grep/ls/exit code）；Type B = 有明确评价对象和证据形式的人类判断，不伪装成机器谓词**。每个条件必须标注**「证明什么」**：是证明**实现存在/运行事实**（证据定位器 + 代理指标），还是证明**结果/价值**（结果标准——通常只能 Type B）。存在性证明不得充当价值结论。例：❌"防止AI产出给人消化" → ✅"<截止日>前在README写下3个具体用途，且每个用途有对应脚本/文档佐证（证明：定位器可查；不证明：用途真被使用）"
2. **maker ≠ checker**——做评审的AI不能同时做验证（给自己打分太宽松）。验证者应是**机械闸（脚本）**或**独立的只读检查**，不能是"我觉得做完了"。v1.7 如实补充：**确定性脚本不天然独立**——同一执行者写的闸 = 可复跑检查；独立性还可来自判据设计与覆盖范围的独立审查、或独立执行角色，按风险级别取用

### 条件的硬谓词写法（setpoint 规范）

"有条件过"的每个条件必须包含（且**只有"被采纳的承诺"才配拥有条件**）：
- **截止日期**（YYYY-MM-DD，不能是"尽快""以后"；禁止"持续项"式无截止条件——那是开放式跟踪的坏样本）
- **可检查的完成标准**（Type A：文件存在否、脚本跑通否、待办追踪状态否——必须能用 grep/ls/exit code 判定；Type B：写明**评价对象与证据形式**，由人判定，不伪装成机器谓词）。写法 = **语义 + 具体定位器**，**禁裸字符串 grep**（反面教材：某交易域 SOP C1 的"无操作日不推送"字面串——实现换位置即出现"闸查不到、实质已达成"的假 BLOCK/假核销，评审记录台账 2026-10-15 交易条目已留痕）
- **「证明什么」标注**（v1.7 新增）：本条件证明的是实现存在/运行事实，还是结果/价值；Type A 证据不得替代 Type B 结论
- **验证方式**（Type A 机械闸自动查 / Type B 需作者判断）

反面例子（不可检查）：
- "改善用户体验"
- "防止AI产出给人消化"
- "明确实际用途"

正面例子（可检查）：
- "<截止日>前在 `<项目目录>/README.md` 写下3个具体用途，每个用途有对应脚本/文档路径佐证"
- "2026-10-31前 `<项目脚本>/<指标报告脚本>` 输出中包含'任务完成率'字段，且近7天报表非空"
- "2026-11-01前 待办追踪库（active 区） 中该项目相关待办 ≤2 条，且无超过30天未动的条目"

### Type A / Type B 分离（验证分类）

| 类型 | 定义 | 验证方式 |
|---|---|---|
| **Type A** | 完全可自动化的机械检查（文件存在、脚本exit code、git提交频率、待办追踪状态、截止日期是否到期） | 机械闸自动验证，不需要人 |
| **Type B** | 人类判断门（项目丰容价值是否真的提升、是否真的没有退化、主观质量判断） | 必须作者批准，AI不能自己关账 |

闭环的工作 = **自动化 Type A 到底 + 可靠地把 Type B 路由给作者**。⚠️ Type A 全绿 ≠ 项目达标——Type A 只验实现/运行事实，价值判断永远在 Type B 侧。**单次成功与可靠性分离（v1.13）**：单次成功只证明发生过；概率性或无人值守机制需要可靠性结论时，须重复运行并报告次数 n 与失败数，样本不足标「待验证」，不写「稳定/可靠」。次数按风险与成本定，不设统一 k，不强制统计模型。

### 闸的措辞与证据边界（v1.8 新增，源自 C4 假归属事件）

- **告警措辞不得断言闸没有的能力**：每条告警/报告的措辞逐句问「这是本闸能证明的吗？」——闸只能答「窗口内有没有改动」，措辞就不得答「是谁改的」。会稳定说错话的闸比会漏报的闸更糟（漏报损失一次覆盖，说错话损失长期信任——骗人一次就会让人对告警脱敏）。
- **闸输出作证据必须写明证明边界**：凡 Type A/B 条件用到某个闸的输出作证据，必须同时写明该输出能证明什么、不能证明什么（闸的盲区）——否则条件会把闸的盲区当成自己的判据（实证：C4 告警无归属能力，却一度被写成重评触发条件的归属证据，直到一次假阳性才暴露）。

### 闭环状态机

```
评审输出结论
    ↓
仅「被采纳的承诺」改写为硬谓词 → 挂 TRACKING.md（待办追踪）（同一真实决策复用一个记录，条件按风险合并，不一条件一文件）
    ↓
机械闸定期扫描（接入 （收尾体检脚本，本包未附带） §5）
    ├─ 条件未到期 → 静默，不打扰
    ├─ 条件到期且满足 → 标记待确认（不自动归档）
    ├─ 条件到期未完成 → Surface（报告级，见下）
    └─ Type B 条件到期 → 提醒作者判断
    ↓
终态（六选一）：继续 / 限额试验 / 缩减 / 暂停 / 停止（显式停止追踪 = 合法结束）/ 接受残余风险
    ↓
是否重新评审 = 仅当「尚有价值判断未决」或「项目发生实质变化」（主版本变更/权限面变化/用途改变）——不一律重开
    ↓
归档（待办追踪库移入 archive 区，评审记录台账追加记录；停止/缩减/接受残余风险均为正式归档理由）
```

### Surface 动作（条件到期未完成时）

当机械闸发现条件到期未完成时，AI 的动作有精确名称：**Surface**——
- 停止当前循环
- 发出简短情况描述（哪个条件、到期多久、尝试过什么、当前状态）
- **等待作者指示**
- **不自动重试、不自动降级、不静默重置、不自己把条件改宽松**

这跟"执行权恒归作者"原则一致——到期未完成是需要人判断的事（是延期？还是放弃？还是条件本身定错了？），AI 不能替人决定。Surface 后作者的合法处置包括：**延期 / 放弃 / 修正条件 / 停止追踪**——"停止追踪/放弃"是正式结束，归档不视为失败、不留心理债务（维度三退出策略在闭环侧的落地）。

### SURFACE / WARN 分离（机械闸的判决层级，v1.7 正名）

机械闸的输出分两层：
- **SURFACE（报告级；旧名 BLOCK/fail-closed——名过其实，v1.7 正名）**：客观可判定的事——条件已过期、格式不完整、必需字段缺失。**实际作用如实标注**：在 wrap-up 体检报告中标红 + 退出码非 0；它**不阻断任何受控动作**（不拦提交/部署/发信，也不拦无关事项的收尾），一处条件逾期不影响其他项目。
- **WARN（提示级）**：主观判断——"这个项目可能在沉迷区投入过多""这个条件的完成标准可能太宽松"。只打印不阻塞。

**永远不要让主观判断升级。** 客观逾期 = 作者该看见的事，不是该被闸拦住的事；一个会因为"AI觉得项目不够好"就阻断的机械闸，会被作者关掉。

### 跟铁律的兼容性

- **零队列**：条件挂待办追踪库 是待办队列——豁免依据**不是**"这是'该做的事'队列"（那是循环论证，v1.7 废止），而是**效果**：每个条件有截止、做完即翻篇、未到期静默不打扰，不构成非自愿义务；若条件开始要求人逐条确认/按节奏进场，即触发维度四审查。
- **纯触发**：机械闸只在 wrap-up 时扫描，不主动推送；条件到期才 Surface。
- **干预完即翻篇**：承诺落地 → 六态终态 → 归档，不持续追踪；重评仅在尚有价值判断未决或实质变化时触发。
- **单条输出**：每次 Surface 只报告一个条件的情况，不堆一堆。

### 跟现有机制的关系

- **待办追踪库**：条件追踪复用宿主环境的待办追踪机制（若有）（已有 frontmatter、lint、看板、周度冲刷），不另建追踪系统。**同一真实决策复用一个 待办追踪库 文件**（v1.7：条件按风险合并，不再一条件一文件），type=`fengneng-condition`，trigger=评审条件。
- **（收尾体检脚本，本包未附带）**：机械闸接入 §5，跟 cabinet_lint/reverse_door/console_window_lint 并列。
- **评审记录台账**：重新评审的结果追加到台账，保留历史不删。评审条目里加「闭环状态」字段（open/conditions-met/pending-rereview/closed）。
- **版本号维护**（第8步）：重新评审时如果项目主文档版本号变了，按版本号规则判断是否需要重新评审。

## 迭代机制

- 框架维度和问法只在本文件维护，改一处即生效
- 每次评审的"框架体感"字段是迭代的唯一输入来源，不另建反馈渠道
- 复盘触发两线（新增≥5 / 体感谱≥2 条评审）由机械闸判定（`scripts/fengneng_review_followup.py`，口径见使用流程第 9 步）；复盘本身 = 作者主导，Agent 辅助汇总体感模式
- **追认制（v1.12 新增，第四轮复盘，作者 2026-10-26 拍板）**：作者当场显式授权的单点改动（先例 = v1.10 历史口径问法、v1.11 触发机械判定）**可即时落地**，不必等复盘批处理；但须同步在评审记录台账「下次框架复盘议程」登记留痕、由下轮复盘逐条追认。**无授权的方向性改动必须等复盘**——追认制合法化的是"作者拍板的快道"，不是 agent 自行改框架。
- 复盘后更新本文件版本号 + 记修订说明（落点见文末「references 索引表」），评审记录台账保留历史不删
- 维度可以增删、问法可以改、输出格式可以调——但每次改动必须在 `references/HISTORY.md` 记一笔（倒序、条目格式不变；什么时候读它 → 见文末「references 索引表」）
